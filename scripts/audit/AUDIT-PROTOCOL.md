# 전수 감사 규약 — 산출 형식과 검토 절차

감사(글을 훑어 오류·빠진 근거·표기 문제를 찾아 고치는 작업)를 **매번 다시 설계하지 않기
위한** 문서다. 2026-08 감사는 ad-hoc 이었고(마크다운 노트 + 카테고리별 표 + 두 벌의 반영
기록), 그 결과를 판본 비교기에 붙이는 데 파서를 따로 썼다. 다음부터는 아래 형식으로 낸다.

산출물은 **버전 관리하지 않는다** (`notes/` 는 gitignore). 일회성 파일이고, 감사의 결과는
글 수정 커밋 자체에 남는다. 형식만 이 문서로 남긴다.

## 1. 작업은 브랜치에서

```
git switch -c audit/<slug>        # 예: audit/2026-11
```

감사 수정은 이 브랜치에만 쌓고, `main` 은 손대지 않는다. 비교기는 `main ↔ audit/<slug>` 로
본다. 검토가 끝나면 그때 병합한다.

2026-08 감사는 main 워킹트리에서 진행했다. 결과적으로 문제는 없었지만(전후 스냅샷을 구워
비교했다), 그 때문에 크론 워커의 커밋이 감사 변경과 섞여 "이후" 쪽이 검토 중에 계속
움직였다. 브랜치를 쓰면 그 문제가 사라진다.

## 2. 산출 파일

```
notes/audit-<slug>/audit.json          ← 비교기가 읽는 정본
notes/audit-<slug>/audit.<무엇이든>.json  ← 나눠 내도 된다 (아래)
notes/audit-<slug>/…                   ← 그 밖의 작업 파일 (자유)
```

`audit*.json` 만 형식이 고정이다. 나머지(작업 로그·재시작 스크립트·중간 보고)는 감사
때마다 편한 대로 둔다.

**여러 파일로 나눠도 된다.** 비교기는 `notes/audit-<slug>/audit*.json` 을 전부 읽어 하나로
합친다 (slug 는 **폴더 이름**에서 온다). 카테고리별·배치별로 떨어뜨리는 게 자연스러우면
그렇게 내면 된다:

```
notes/audit-2026-11/audit.commutative_algebra.json
notes/audit-2026-11/audit.scheme_theory.json
```

합치는 규칙: 같은 글(`path`)이 여러 파일에 나오면 항목을 이어 붙이고 `id` 로 중복을 지운다.
`title`·`base_ref`·`generated_at` 은 처음 만난 값을 쓴다 — **`base_ref` 는 파일마다 같아야
한다**(다르면 서로 다른 판본을 한 감사로 합치게 된다).

## 3. audit.json 형식

```jsonc
{
  "schema": "blog-audit/1",
  "slug": "2026-11",
  "title": "가환대수 카테고리 감사",
  "base_ref": "10a818f378bd8c884cf34d40b489f78217c4f867",  // 감사 대상 판본 (수정 전)
  "generated_at": "2026-11-03T14:00:00+09:00",
  "posts": [
    {
      "path": "_posts/Math/Algebraic_Structures/ko/2021-09-02-Algebraic_Structures.md",
      "verdict": "needs_user",        // fixed | needs_user | clean
      "note": "…",                    // 글 단위 비고 (선택)
      "items": [ /* 아래 */ ]
    }
  ]
}
```

### 항목(item) — **diff 블록 하나당 하나**

이게 이 형식의 핵심 규칙이다. 한 항목은 **수정 전 파일의 블록 하나**(문단·정리 박스·
display 수식·도식 하나)에 대응한다. 한 블록에서 여러 가지를 고쳤으면 그 항목의 `summary`
안에서 나열하고, 항목을 쪼개지 않는다. 반대로 한 지적이 여러 블록에 걸치면 블록마다 항목을
만든다(같은 `group` 을 달아 묶는다).

```jsonc
{
  "id": "BUG-1",              // 글 안에서 유일. 종류-번호 관례를 권한다
  "kind": "BUG",              // BUG | GAP | STYLE | QUESTION (자유 확장 가능)
  "group": "BUG-1",           // 여러 블록에 걸친 한 지적을 묶는 키 (선택)

  "quote": "…",               // ★ 위치를 특정하는 인용문 — base 파일 원문 그대로
  "base_lines": [31, 40],     // base 파일 기준 줄번호 (선택, 인용문 중복 시 가려내기용)
  "was": "$x\\ast y$",        // 그 블록 안에서 실제로 바뀐 조각 (선택)
  "now": "$x\\star y$",       // 위의 수정 후 (선택)

  "summary": "…",             // 한 줄 요약
  "fix": "…",                 // 수정안 (선택)
  "detail": "…",              // 마크다운 전문 (선택) — 호버 카드에 그대로 뜬다
  "status": "applied",        // open | applied | dismissed
  "resolution": "…"           // 어떻게 처리했는지 (선택)
}
```

**인용문 규칙** — 이게 매칭의 전부다.

- **base 파일(수정 전)의 원문을 그대로** 옮긴다. 렌더된 화면에서 긁은 글자가 아니다.
  수식은 `$…$` 형태 그대로 둔다.
- **본문 내용만** 적는다. `::: 정의 3` 여는 줄, `##` 제목 마크, 목록 마커(`-`·`1.`),
  인용 마커(`>`), `{% diagram … %}` 같은 표기는 렌더된 본문에 남지 않으므로 인용문에
  넣으면 그 항목은 어느 블록에도 안 붙는다 (2026-08 데이터 변환 실측: 초기 미매칭
  803건 중 71%가 `:::` 여는 줄이었다. 걷어내니 91건으로 줄었다).
- **그 글 안에서 유일할 만큼 길게.** 낱말 하나(`open`)로는 위치가 안 잡힌다. 문장 단위가
  기본이고, 필요하면 두 문장까지 간다.
- 인용문은 **화면에 그려지지 않는다.** 표시되는 빨간 마크는 diff 계산 결과뿐이고, 인용문은
  "이 항목이 어느 블록 얘기인지"를 정하는 데만 쓴다. 그래서 길어도 손해가 없다.
- 실제로 고친 짧은 조각은 `was`/`now` 에 따로 적는다. 그게 있으면 비교기가 그 블록의 여러
  변경 중 정확히 하나에 카드를 붙인다.

**왜 base 기준인가** — base 는 스냅샷이라 불변이다. 줄이 밀리는 건 수정 *후* 파일인데,
비교기는 after 줄번호를 쓰지 않는다. 블록 정렬기가 이미 base 블록 ↔ after 블록을 맺어
놓기 때문이다:

```
항목 → (quote·base_lines) → base 블록 → [정렬기] → after 블록 → diff 마크
```

이 고리에 밀림이 끼어들 자리가 없다. 플레이스홀더를 심었다가 걷어내는 식의 보정은 필요
없다.

## 4. 비교기가 하는 일

`/dash/compare.html` 은 `notes/audit-*/audit.json` 을 훑어 감사 목록을 만들고, 고른 감사의
`base_ref` 를 "이전" 판본의 기본값으로 쓴다. 글을 열면:

1. 항목의 `quote` 로 **base 블록**을 찾는다 (공백·수식 구분자·강조 기호를 지운 뒤 비교).
   중복되면 `base_lines` 로 가려낸다.
2. 그 블록에 걸린 diff 마크에 카드를 붙인다. `was`/`now` 가 있으면 그중 하나로 좁힌다.
3. **미반영 의심**: `status: "applied"` 인데 그 블록에 변경이 하나도 없거나, `was` 가 after
   쪽에 그대로 남아 있으면 경고로 표시한다. 이건 diff 만 봐서는 절대 안 보이는 부류다
   (2026-08 실사례: 세 군데를 고치라는 지적에서 두 군데만 고쳐졌다).

   이 판정은 **항목이 블록 단위일 때만** 뜻이 있다. 한 항목이 여러 줄을 가리키면 그중
   맥락으로 인용한 줄까지 "안 고쳐졌다"고 잡힌다 (2026-08 변환본 실측: 의심 511건 중
   307건이 여러 블록으로 쪼개진 항목에서 나왔다). §3 의 "블록 하나당 항목 하나" 규칙이
   이것 때문에 있다.

## 5. 검토 절차

1. `python3 scripts/dashboard/snapshot.py <base_ref>` — 수정 전 판본을 굽는다 (~100초).
   비교기에서 판본을 고르면 없을 때 자동으로 굽기도 한다.
2. `/dash/compare.html` 에서 감사를 고르고 글을 훑는다. 변경 위에 마우스를 올리면 그 지적의
   요약·수정안·전문이 뜬다.
3. 고칠 것은 본문에서 문장을 끌어 선택하고 **메모**로 지시를 적는다. 위치는 인용문으로
   잡히므로 마크다운을 열 필요가 없다.
4. **지시서 복사** → Claude 세션에 붙여넣는다. 서버에서 바로 가져와도 된다:
   `curl -s http://127.0.0.1:8089/api/compare/instructions`
5. 세션이 반영을 마치면 지시서 끝의 명령으로 **그 메모들을 지운다**
   (`python3 scripts/dashboard/notes_cli.py --del <id …>`). 메모는 브라우저가 아니라
   Pi 에 있으므로, 지우지 않으면 다음 검토 때 이미 처리된 지시가 다시 나온다.

## 6. 감사를 돌리는 쪽에 주는 지침

여기부터는 **감사를 수행하는 모델이 그대로 따르는 규격**이다.

### 6.1 블록이란 (조작적 정의)

`base_ref` 판본의 그 파일에서 **빈 줄로 끊긴 덩이 하나**다. 구체적으로:

| 덩이 | 한 블록인가 |
| --- | --- |
| 문단 하나 | 그렇다 |
| `::: 정의 3 … :::` 박스 | **통째로 하나** (안의 문단·수식을 쪼개지 않는다) |
| `$$…$$` display 수식 | 그렇다 (앞뒤 문단과 별개) |
| 목록 하나(`-`/`1.` 연속) | **통째로 하나** (항목별로 쪼개지 않는다) |
| `{% diagram … %}` 도식 | 그렇다 |
| `##` 제목 줄 | 그렇다 |

한 블록에서 세 군데를 고쳤어도 **항목은 하나**다. `summary` 안에서 나열한다. 반대로 한
지적이 두 블록에 걸치면 **항목 둘**을 만들고 같은 `group` 을 단다.

### 6.2 항목 하나를 쓰는 순서

1. 고칠(또는 지적할) 블록을 정한다.
2. 그 블록에서 **문장 하나를 원문 그대로 복사**해 `quote` 로 삼는다. 마커(`:::`·`#`·`-`·
   `>`·`{%`)로 시작하지 않는 줄에서 고르고, 글 안에서 유일할 만큼 길게 (짧으면 두 문장).
   줄바꿈은 공백으로 접어도 되지만 **글자는 바꾸지 않는다** — 수식은 `$…$` 그대로.
3. `base_lines` 에 그 블록의 줄번호를 적는다 (같은 문장이 여러 번 나올 때 가리는 용도).
4. 실제로 바꾼 짧은 조각이 있으면 `was`/`now` 에 적는다. **`was` 는 base 파일에 그대로
   있어야 한다** — 없으면 아예 비워라. 억지로 채우면 "미반영 의심" 판정이 오염된다.
5. `summary` 는 한 줄로 무엇이 문제인지. `fix` 는 어떻게 고칠지. `detail` 은 근거 전문
   (마크다운, 길어도 된다 — 호버 카드에 그대로 뜬다).
6. `status` 를 정한다:
   - `applied` — 이 감사에서 실제로 고쳤다
   - `open` — 지적만 하고 안 고쳤다 (사용자 판단이 필요하거나 범위 밖)
   - `dismissed` — 살펴봤는데 문제가 아니었다 (기록만 남긴다)

### 6.3 반드시 지킬 것

- **고친 것도 전부 항목으로 낸다.** 항목 없이 고치면 비교기에서 "지적 없는 변경"으로 떠서
  사용자가 근거를 못 찾는다.
- **안 고친 것도 전부 낸다** (`status: "open"`). 안 내면 그냥 사라진다.
- 인용문은 **base(수정 전) 원문**이다. 수정 후 파일에서 따오면 안 붙는다.
- 줄번호만으로 위치를 지정하지 않는다. 줄번호는 보조다.
- 렌더된 화면에서 긁은 글자를 쓰지 않는다 (`\(…\)`·병기 첨자가 원문과 다르다).
- 수식·기호·용어는 글의 관례를 따른다 (`_posts/Math/CLAUDE.md`, GUIDELINE).

### 6.4 예시

수정 전 파일(`base_ref`)의 한 문단:

```markdown
이항연산 $\star$의 함수값 $\star(x,y)$는 $x\ast y$로 줄여쓴다. 마그마는 집합 $A$ 뿐만
아니라 그 위에 정의된 연산까지도 포함하는 구조이므로, 문맥상 명확할 경우를 제외하면
마그마를 나타낼 때에는 $(A,\star)$와 같이 연산과 집합을 모두 표기해준다.
```

이 문단의 `$x\ast y$` 를 `$x\star y$` 로 고쳤다면:

```json
{
  "id": "BUG-2",
  "kind": "BUG",
  "quote": "이항연산 $\\star$의 함수값 $\\star(x,y)$는 $x\\ast y$로 줄여쓴다.",
  "base_lines": [26],
  "was": "$x\\ast y$",
  "now": "$x\\star y$",
  "summary": "축약 표기를 도입하는 문장이 정작 다른 기호($\\ast$)를 쓴다.",
  "fix": "$x\\star y$ 로 고친다. 이 글은 정의 1부터 끝까지 연산이 $\\star$ 다.",
  "status": "applied",
  "resolution": "고침"
}
```

### 6.5 넘기기 전에 자체 점검

```
python3 scripts/audit/validate_audit_json.py notes/audit-<slug>/
```

**인용문이 base 파일에 그대로 있는지**를 기계로 확인한다 (이게 틀리면 비교기에서 그 항목은
에러 없이 그냥 안 뜬다). 그 밖에 id 중복·`status` 값·필수 필드·마커로 시작하는 인용문·
`base_ref` 불일치를 잡는다. **오류 0** 으로 만들고 넘긴다. 경고는 판단해서 남겨도 된다.
